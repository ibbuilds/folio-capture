# Technology choices for the collection engine

Research checked 12 October 2026. The goal is fast, effective collection with low resource use across source-guided capture, calibration and eventual autonomous source expansion. The future library UI/MCP remains separate. Documentation establishes capabilities and constraints; local benchmarks establish only the tested workload's performance.

## Comparison and current decisions

| Layer | Alternatives examined | Decision for the local engine |
|---|---|---|
| Dependencies | npm, pnpm, Bun install | Adopt pinned pnpm: repeat installs were about 70% faster here. One lockfile; scripts remain accessible with `npm run`. Bun install is a credible alternative, but was not benchmarked in this study. |
| Runtime | Node native TypeScript, tsx, Bun, Rust | Keep Node 24; remove tsx/esbuild. Native TypeScript reduced CLI startup about 33%. Bun's local Windows compatibility pilot failed cleanup contracts. Rust remains a candidate for measured CPU kernels, not an assumed browser speedup. |
| Rendering | Playwright, Puppeteer, raw CDP/chromiumoxide, headless shell | Keep pinned full Chromium with Playwright. Puppeteer and Rust drivers still render through Chrome. A driver rewrite has no demonstrated throughput benefit here. Headless shell is faster in some workloads but is not behaviorally identical to full Chrome. |
| Discovery | Browser traversal, HTTP + HTML parsing, Crawlee | Retain tested adapters now. Prioritize adapter-specific HTTP discovery where links are present in responses; retain browser fallback for hydration and infinite scrolling. Crawlee is a useful future scheduler candidate, not an immediate replacement of the durable ledger. |
| Images | Sharp/libvips, Bun.Image, Rust image/PNG kernels | Keep native Sharp, and avoid work through browser clipping. Faster low-compression PNGs increased disk use. Bun.Image deserves its own fidelity/speed test before adoption; no comparative measurement is claimed. |
| State and jobs | SQLite WAL, PostgreSQL, BullMQ | Keep SQLite for one local run and a coordinator. A distributed deployment needs a shared database/queue; evaluate PostgreSQL/BullMQ then, with leases and idempotency. Do not share SQLite WAL over a network filesystem. |
| Classification | Existing isolated CLI jobs, batching/parallel workers, alternate model services | Preserve existing authentication and validated per-subject evidence. Cache and resume saved work. Future bounded scheduling must respect account limits and exact subject boundaries; a cheaper model needs held-out aesthetic/quality evaluation. |

### What the sources establish

[pnpm's linked dependency structure](https://pnpm.io/symlinked-node-modules-structure) shares package contents through a store and links. The local install comparison measures the benefit in this small project; it is not a crawler runtime benchmark. The [pnpm 12 release](https://pnpm.io/blog/releases/12.0) also describes implementation changes. Installed tool versions are pinned rather than selected dynamically on each run.

[Node's TypeScript documentation](https://nodejs.org/docs/latest-v24.x/api/typescript.html) marks stripping stable from 24.12 and explains its syntax limits. Our configured minimum is 24.15. Explicit fields replace two parameter properties, and `erasableSyntaxOnly` plus `verbatimModuleSyntax` prevent introducing syntax/imports that would require transformation. Type checking remains separate.

[Bun's compatibility matrix](https://bun.sh/docs/runtime/nodejs-compat) documents Node API differences, while [Bun 1.4](https://bun.sh/blog/bun-v1.4) reports Playwright and SQLite improvements. Therefore Bun was tested, not dismissed based on older compatibility information. Bun 1.4.3's Windows binary was downloaded from its official release with its published SHA-256 verified. In a 26-test pilot, all seven screenshot tests passed, but 16 tests failed during directory removal after SQLite use (`EBUSY`), including cleanup after `close()` and retrying removal. Ten passed overall. This blocks claiming it is a drop-in supported runtime on our platform; it does not prove database corruption or universally poor Bun performance. No throughput ranking is claimed from failed tests.

[Puppeteer's headless documentation](https://pptr.dev/guides/headless-modes) explicitly distinguishes full Chrome from the faster, separate shell. [Playwright's browser connection documentation](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp) warns that its CDP connection has lower fidelity than its own protocol. [chromiumoxide](https://docs.rs/chromiumoxide/latest/chromiumoxide/page/struct.Page.html) supplies a Rust Chrome driver and screenshot API. These capabilities do not establish that either replacement improves this engine's clean-capture pipeline. Full-browser rendering, fresh contexts and state/viewport evidence are the current requirements.

[Crawlee's Playwright crawler documentation](https://crawlee.dev/js/api/playwright-crawler) recommends HTTP/Cheerio crawling for pages that do not require JavaScript and reports a large general speed advantage. Treat its claimed multiplier as upstream guidance, not our measured result. HTTP discovery can cheaply extract explicit links, but cannot replace rendering for screenshots or prove that an infinite collection is exhausted. [Conditional HTTP requests](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Conditional_requests) can save transfers where validators exist; unchanged HTML alone does not prove that every CSS/JS/image or viewport rendering is unchanged.

[Sharp's performance guidance](https://sharp.pixelplumbing.com/performance/) explains native libvips and libuv/thread concurrency. Node orchestration does not mean JavaScript performs the image kernels. Increasing thread counts is not free: simultaneous browsers and images compete for memory/CPU. [Bun.Image](https://bun.sh/docs/runtime/image) offers native PNG/WebP and resize operations without an addon, but API availability is not proof of equivalent pixels, color, clipping or throughput.

[SQLite WAL](https://sqlite.org/wal.html) supports readers alongside one writer on one host; that matches the current single-run lock. [BullMQ concurrency guidance](https://docs.bullmq.io/guide/parallelism-and-concurrency) distinguishes I/O concurrency from CPU parallelism. Its current [PostgreSQL backend](https://docs.bullmq.io/guide/postgresql) is another option alongside Redis, so a later shared queue need not imply two database services. Its published job benchmarks are not Folio Capture benchmarks.

## Alignment with the phases

1. **Source-guided beta:** retain predictable local installation, tested source adapters, persistent separate stages, six faithful viewport profiles and accepted-candidate exports. Shipped performance changes remove repeated metadata parsing and image processing. The next high-value experiment is HTTP discovery within an adapter, comparing discovered identities, provenance and stopping reasons against browser traversal.
2. **Creator examples and calibration:** keep images/evidence reusable offline. Evaluate models, prompts, sampling and optional retrieval of creator-approved examples on fixed held-out sites/viewports. Save assessments and critiques independently so interruption does not repeat successful work. Concurrency or batching must not let one section's labels/quality leak into another or skip a critique. The current study calls no models and establishes no semantic accuracy.
3. **Gap-directed expansion:** add bounded HTTP fetch pools and per-origin budgets before multiplying browser processes. Separate lightweight discovery workers from expensive rendering/analysis workers. If multiple hosts become necessary, use a shared queue with renewable leases, recovery and atomic capture publication; preserve stable IDs and the file/data contract. Measure PostgreSQL/BullMQ/Crawlee against the required workload before choosing. Calibrate usefulness of new sources with inspected candidates; the system's own classifications are not independent ground truth.

## Decision rule for the next changes

Measure wall time, total process-tree CPU/RAM, transferred bytes, stored bytes, recovered jobs, discovery completeness and valid capture coverage on the same fixture set. Record p50/p95 on representative collected workloads when live trials are authorized. Adopt an alternative only when it improves the relevant budget without losing fidelity, exact-scope decisions or recovery. Favor a native Rust component when profiling identifies substantial remaining CPU-bound work that existing native libraries cannot address. Favor a distributed service when the local coordinator is the measured operational limit. Neither condition has been established by this study.

HTTP discovery, distributed queues, browser concurrency, Bun.Image, alternate classifiers and automatic source expansion are researched next steps, **not shipped features**. This document is a technology decision record, not a claim that the engine has implemented all future phases.
